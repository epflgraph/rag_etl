At CEDE (EPFL) we are currently building educational AI tools for students. We do have two systems currently: AI chatbots and AI bots that reply in forums, both based on course materials via RAG.

A bit of history and context:
- In 2022 I was hired as part of the EPFL Graph team (within the CEDE team), a knowledge graph based on EPFL data. Our mission was to institutionalise the project, consolidate the database and create the GraphSearch website, a frontend to make this accessible. I joined together with two colleagues: Thijs was in charge of the frontend, Ramtin was in charge of the concepts ontology that would link other nodes semantically and I was in charge of algorithms. Yves was already in charge of the data collection and generation of the raw database and Francisco was the coordinator of the project. Ramtin and I created the GraphAI API (`graphai`), an API that exposes endpoints for OCR, extraction of subtitles from videos, voice transcription, concept detection in texts, etc.
- In 2023, the project was consolidated and as ChatGPT gained traction, Francisco asked me to create a chatbot to expose the EPFL Graph data using the OpenAI API, which I did. The chatbot shared the database with GraphSearch so that both were in sync.
- Later, at CEDE we were exploring options to provide AI solutions both to EPFL staff and students. Since EPFL Graph is part of CEDE, we started a prototype to add RAG to the chatbot. We scraped the EPFL rules and regulations website and built a custom RAG database (elasticsearch) more or less manually. I added a flag to the chatbot so that it would fetch data there instead of the data from EPFL Graph. After this prototype, a few other followed (one with service académique, another with servicedesk, etc.). The obvious next step, given that CEDE is in charge of digital education at CEDE was an educational chatbot based on course material.
- In collaboration with a professor, we manually indexed their material in the RAG database and I created yet another prototype chatbot for their course.
- In parallel, Javier had joined CEDE and, since the RAG database was already built, he had started working on a forum bot that would use LLMs to answer student questions in the course forum using the same RAG database.
- Quickly we needed to scale to other courses, so Ramtin started working on the `chatbot-pipelines` repo, to more or less automatise what we had previously done manually to index the RAG material. For that, he leveraged GraphAI, which already had algorithms to do OCR, to embed text, etc. However, course material is messy, so Javier and I agreed with Ramtin that we would preprocess the material to make it digestible for the pipeline. More specifically, next to the course material we would hand a metadata file with lots of information about each of the files (what type of material, its number/subnumber, how to chunk it, whether there was a release date, etc.). The goal was not only to process the material correctly but also to be able to filter later when retrieving the chunks. Also, we were dropping the file dumps on a shared Google Drive and Ramtin was retrieving them from there for the pipeline.
- This worked at the beginning but quickly the preprocessing was still too heavy for Javier and me to keep doing it manually. Ramtin left the team so not to break too much of the pipeline I decided to create the `rag-prepipeline` repo. This would draw documents directly from Moodle and other sources and automatise the generation of the metadata files, plus some more functionalities like cutting an exercise pdf in one chunk per exercise. The idea was that composing the `rag-prepipeline` with Ramtin's `chatbot-pipelines` would give an end to end solution to index the RAG documents from the source to the RAG database.
- At the same time, EPFL made available an LLM inference platform called RCP. This exposed AI models for us to use at no cost and with all data remaining in-house. Up to that point, we had been using commercial services for most of our tasks, but this made us reconsider and switch to this in-house solution. In addition, we wanted to avoid the pipeline communication via Google Drive, which we replaced with simple communication over files on the disk of the same machine. Our goal was to have everything contained at EPFL so that professors and students wouldn't need to worry about privacy. After changing a few things, we succeeded, and last semester already everything was running within premises.
- However, it's now 2026 and we have accumulated quite some technical debt. GraphAI was designed and built right before the AI burst and before RCP was created. `chatbot-pipelines` was created making many choices that don't really apply anymore. I have updated it a couple times, but only making surgical changes to fix some bugs while trying not to break anything else. At this point, since Ramtin left, nobody understand the `chatbot-pipelines` repo, but we think things could be done better, and soemtimes we observe remnants from the past that we thought were behind (e.g. a mention to google drive still in the cache database). In addition, our current RAG pipeline consists of two pieces of independent software that are composed together through a cumbersome intermediate metadata file that probably isn't be needed anymore, and both of which do similar things (e.g. exercise pdfs are OCRd, stitched and chunked meaningfully in the `rag-prepipeline`, but slides are OCRd in the `chatbot-pipelines`).
- To pay this technical debt, we are now willing to do the following things:
  - We want to promote the `rag-prepipeline` repo to be the only RAG pipeline (called `rag-etl`), that works end to end. For that, we need to merge certain functionalities from the `chatbot-pipelines` that are missing, and create a loader that actually populates the elasticsearch RAG database. While doing this, we can refactor `rag-prepipeline` as needed.
  - The resulting `rag-etl` unified pipeline must be in charge of RAG not only for courses (although they are the main use case), but also for other projects: other educational AI tools (e.g. debate partner for a course, explique chatbot and others), as well as other non-educational AI tools, like admin chatbots (`lex`, `servicedesk`, etc.) or bots for specific labs (e.g. `plasma`, `cmi`, etc.). 
  - Once this is done, we want to discontinue `chatbot-pipelines`, as it will not be needed anymore.
  - We need to rethink what is delegated to `graphai` now that we have AI models available on RCP. Among the things that need to be considered are: do we need graphai to embed texts? Who and how does the OCR? Who is in charge of caching (right now, `rag-prepipeline` caches in the disk, but `chatbot-pipelines` delegates caching to `graphai`, which uses a cumbersome database schema and connector to do so)?
  - As a final product, we want to make `rag-etl` an excellent, modern piece of software, taking best practices into account, simplifying when possible, avoiding duplication via modularity and leveraging existing libraries when reasonable. 
    
The goal is not so much to preserve exact functionalities but to be able to continue offering both services that consume the RAG database (and possibly more in the future). Avoid just "copying" functionalities over, and instead question if we still want to do something in the same way or if it would be better to change it, improve it, or perhaps drop it.
